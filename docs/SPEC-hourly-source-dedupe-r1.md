## 1. 用户能得到什么

同一来源在同一小时被手动、定时多次触发时，后续构建使用已保存内容，不把来源重新完整抓一遍。失败会说明原因和下次可尝试时间；旧内容继续可读。下一小时到期后，在下一次实际运行时补抓，不承诺 GitHub 准点执行。

这是采集调度的增量，不改变页面、热点计算、条目去重、已准入来源或发布方式。PR #13 的 cron、PR #14 的视觉审核独立进行。

## 2. 已有决定与本次建议

以下来自固定版本的既有决定：逐规范源记录尝试/成功时间、批次、游标和错误；同源别名不增加整轮次数；push 的 NO_FETCH 路径不抓源；支持缓存、条件请求、退避及部分失败；不绕过访问限制，不改 workflow。

以下实现细节是**本次建议，随本 Spec 一起待审**：

| 项 | 建议 |
| --- | --- |
| “一小时” | 只按北京时间自然小时 hour_key 限额，不叠加60分钟间隔。11:07:30与12:07:10均能正常领取；10:59与11:00分属两个批次，可能相邻发生，不能宣称任意60分钟滑窗仅一次。每批资源预算和源级退避仍有效。 |
| 失败次数 | 已开始的失败批次也占本小时额度，不在同小时自动重开整轮。网络/5xx 连败依次退避 1、2、4、8、12、24 小时，之后上限24小时；一次完整成功后清零。 |
| 部分失败 | 已取得的合法新内容保留；任一必要翻页/资源失败标 partial，不伪报完整成功。后续批次从已记录缺口续补。 |
| 安全失败 | 403、验证码、登录要求标 blocked 并停止该入口，后续须人工核对恢复；429 不绕过，遵守有效 Retry-After，且不早于正常到期时间。 |
| 保证范围 | 先覆盖使用同一持久化数据库的采集者，以及现有串行且成功持久化的连续 Actions 运行。独立数据库、丢失状态、远端未持久化的崩溃不具备全局“只抓一次”保证。 |

最后一行是必须正视的限制，不能用本地锁掩盖。若验收要求包括任意重试、崩溃和多机副本的严格全局限制，则本需求实施前必须另行审定共享状态持久化方案；本 Spec 不授予新增服务或改生产配置的权限。

## 4. 建议的数据与执行边界

### 4.1 规范源和资源键

- 采集前按已核实的规范源归并，主键使用稳定来源ID；TG已登记同一 channel 只建一个计划，feed同一已核实端点只建一个计划。
- 现有来源表没有完整 alias 账本。本轮不猜测相似名称、标题或重定向就自动合并；尚未核实的别名列待确认，不擅自替换来源。
- 资源键区分 feed、TG页、详情、图片，绑定规范源和实际端点/页游标。URL保留有语义的路径与查询参数，不粗暴删参数导致不同资源被当成一个。
- 公开/私有来源在计划建立前按原规则过滤。采集状态不进入 HTML、公开索引或图片辅助数据，不放私有来源信息到公开日志。
- 不新增来源、详情爬虫、账号或 cookie。当前无详情采集的适配器不因本 Spec 新增详情请求；以后接入时再复用资源预算。

### 4.2 在现有 tg.db 中扩展状态

建议独立表而不复用 msg/entry/status 的语义：

| 表 | 最小字段/约束 |
| --- | --- |
| source_fetch_state | source_id、last_attempt_at、last_success_at、next_eligible_at、consecutive_failures、status、error_code；source_id唯一。 |
| source_fetch_batch | source_id、北京时间hour_key、attempt_id、started_at、finished_at、status；(source_id,hour_key)唯一。未完成记录不自动删后重开同小时批次。 |
| fetch_resource_state | source_id、resource_key、last_attempt_at、etag、last_modified、materialized_at、representation_valid、error_code；资源键唯一。 |

原 TG gap 保留采集游标及缺口，feed entry 保留已解析条目；不创建第二份内容库，**不把原始HTTP响应体写入 tg.db/git**。复用已物化入库的解析结果和现有 media。只有该资源的完整响应已成功校验、解析并提交，representation_valid 才为真，验证器与该标记同事务提交；合法空 feed 也要记录完整物化结果，不能仅凭有旧条目推断有效。内容重置、解析版本不兼容或数据库清理破坏物化结果时一并清除验证器。条件请求先用于当前 feed 端点；TG分页仅在可证明已完整物化时启用，不能用入口304跳过未完成 gap。批次明细只保留最近7天、当前批次和未结状态；资源元数据随有效源/必要缺口保留，淘汰旧状态不得删除 msg/entry。

纯读 NO_FETCH 不建表、不回填、不发网络请求；不存在新表时仍读旧数据库。正常可写迁移保留旧 msg/entry/gap 和已有来源状态；缺少新状态的源在**首个获准实施后的正常采集**才建立记录，本轮不跑迁移或首次采集。

### 4.3 获取批次、抓取和收尾

1. 使用同一数据库的写入者先取得数据库旁的本机排他采集锁；拿不到则记录 busy，使用已有内容，不启动并行抓取。锁只在本机有效，不宣传跨机互斥。
2. 用短事务检查源 blocked、next_eligible_at、本小时批次；未到期输出 skip_reason；到期原子写入批次和 last_attempt_at，先提交再做网络请求。
3. 每源串行采集；现有多页是同一批次内的有限续页，不是无限请求许可。保留 TG 原翻页/缺口上限和图片并发上限，不提高上限；首次访问各源顺次错开至少1秒，网络失败不即时整轮重试。
4. 同一资源在本批次只尝试一次，图片落盘沿用临时文件+原子替换；下载失败不把半文件当命中。保留查询语义，不跨来源随意共享未核实图片。
5. 有有效物化标记时带 If-None-Match / If-Modified-Since。304表示对应资源未变，保留已入库条目并记本次检查成功，不需要重放响应正文；200必须完整校验、解析、入库后才更新验证器。无有效物化记录却收到304应标 materialization_missing，下一合法批次才无条件请求，不在本批次补打一轮。独立 gap/图片失败不能因入口304被记为已恢复。
6. 保存新增内容、必要缺口和结论；ok才更新 last_success_at，partial/error/blocked保留上次成功时间并记 next_eligible_at。单源失败不阻断其他源，隐私检查和现有持久化失败仍按原有规则阻断发布。
7. 进程中断后释放本机锁，但同小时 running 批次仍占位；恢复时标 interrupted，下一合法批次从保存的缺口续补。SQLite状态丢失时不能宣称已去重；状态损坏应停止采集并报告，不静默重建后抓源。

所有锁和表只属于未来的产品采集设计，**与既有流程试运行状态无关，不读取、迁移或重建后者**。

## 5. 持久化与可证明的限制

正常 Actions 先串行构建、再沿既有路径保存 tg.db；新表随数据库保存。后续干净 runner 只有取得含新状态的数据库才可复用额度。此处只描述现状和兼容设计，不修改或重新运行 workflow，不新增直接推 main 的机制。

同一数据库中，先提交的 attempt记录能在单机进程崩溃后保留；但 runner在远端持久化前被终止、数据库回退/丢失、其他机器使用旧副本时，该事实无法从旧副本恢复。因此：

- 本轮建议先接受“共同持久化状态存在时的逐源去重”，并把故障边界纳入交付说明。
- 多机严格额度、远端崩溃后的严格一次，需要共享的持久状态/独立领取边界；不通过无限续租、另起服务或改权限偷偷补齐。
- 若阿欢要求严格全局保证，实施阶段先停在该阻塞并提交独立方案，不用降低测试要求宣称通过。

## 6. 实施 PR 的离线验收计划

本 Spec 不创建测试代码、不运行真实来源。后续获准实施时，用临时数据库、假HTTP响应、可控时钟和子进程验证：

| 用例 | 必须观察到的结果 |
| --- | --- |
| 同源别名/重复登记、同小时三次调用 | 一次合法批次；后两次零来源/图片请求，已有内容仍可构建。 |
| 11:07:30开始，12:07:10触发（59分40秒） | 跨自然小时，两次均可领取；不因少20秒跳过整小时。 |
| 10:59开始，11:00触发，11:59再触发 | 11:00属于新小时可领取；11:59同小时跳过。该边界可能邻近两轮，显式列为自然小时语义；跨日一致。 |
| NO_FETCH=1 与混合可见来源 | 零网络、零采集状态写入；原有私有来源隔离不倒退。 |
| A失败、B成功；同小时再触发 | A不立即重试，B成功保存；旧内容不被清空，部分失败可见。 |
| ETag/Last-Modified、200→304、无物化记录304、合法空feed、损坏200 | 验证器与已提交解析结果对应；304不丢条目，空feed也能证明有效；损坏/部分解析不启用新验证器，原始响应正文不入库。 |
| 翻页中断和缺口续补、图片失败/临时半文件 | gap不丢；下一到期批次可续补；重复资源不叠加请求。 |
| 同一数据库两进程竞争、领取后中断 | 至多一个进程发起批次；恢复不重开同小时批次。 |
| 403/验证码/登录要求、429、连续5xx、成功恢复 | 阻断/退避原因及next_eligible_at准确；无绕过或高频重试。 |
| 重开同一已保存DB、恢复旧副本 | 前者额度保留；后者明确属于未覆盖条件，不能记作全局测试通过。 |
| 旧库迁移及只读构建 | 原数据、缺口、图片引用保持；只读路径不触发迁移。 |

单源私有路径只进入本机/私有排错，不把原始响应、凭据或全量URL查询写入公开页面。诊断最少记录规范源、批次、result/skip_reason、请求/缓存/新增计数及下一到期时间；last_checked与last_success分开，不把失败刷新伪装为新内容。

blocked由采集器检测并写源级状态；现有总控CI巡检看不到此状态，Luna也只看已投递GitHub工单。因此未来获准上线前，实施PR必须明确一位运行责任人及源级日志/Actions摘要的实际检查、向需求issue报告阻塞的路径，证明无新工单不被当作来源健康。采集器不擅自持凭据发评论。运行责任人核对入口恢复证据后，在另获阿欢同意的维护操作中解除blocked，仍等下一自然小时合法批次，不自动重试或绕过。该监测/通知责任未落实时不得以“全部可观测”验收上线；本轮不创建新例程或变更生产。
