AI已经攻破互联网加密？传闻源头紧急降温：理论突破确实有，但全网传歪了P=NP

最近几天，外网疯传 AI 攻克了计算机科学千禧年难题 P vs NP，即将击穿互联网加密体系。P vs NP 问的是，一道容易验算的题是不是也容易解出来，就像核对填好的大数独很快，但从零解极难。互联网加密靠的正是「容易加密、极难反推」，一旦 P = NP 成立并出现实用算法，金融交易、通信隐私乃至抗量子加密都可能失效。 但这场恐慌把两件事混在了一起。OpenAI 和 Anthropic 这周放出的代数版证明 VP ≠ VNP，指向的是 P ≠ NP，反而在给密码学打地基。真正让人紧张的是另一条传闻：AI 可能找到了在普通电脑上快速分解大质数的捷径。互联网广泛使用的 RSA 加密，全靠「把两个超大质数相乘很简单，反过来拆开却要算上千年」。就算 P ≠ NP 成立，RSA 依然可能不用等量子计算机就被提前攻破。 传闻源头是前 OpenAI 研究员、知名计算机科学家 Scott Aaronson。他发博客称，多个可靠信源证实，顶尖 AI 实验室手里握着未公开的密码学「重磅炸弹」。过去一周，OpenAI 和 Anthropic 在 GitHub 接连放出黎曼猜想等多项重大数学证明，此前的业内风声屡屡成真，这一次没人再敢把密码学风声当谣言。 11 月 27 日，Aaronson 公开降温，划清了边界。他明确表示，AI 实验室确实很快会公布一项理论密码分析突破，但不会对现行加密构成立即危险；至于外界疯传的「攻破 RSA」，连他自己也只是听说、没有任何实锤。 信源 动察 Beating 频道 · 动察 Beating 交流群

这周做了个大活，我在为vibench设计 Coordinator 的核心逻辑以及 UI，这件事前后加起来花了我三天时间

Coordinator 的设计是我一直以来的想法，其根源来自于我的工作流程痛点所经历的三个时期的变化。 第一个时期，我做事情的每个步骤都要开会话，重复输入相似的 prompt。当时的流程是：先开一个 Plan Mode，把 Plan 写出来，然后再开一个会话去 Review Plan；完了之后再去执行，执行完有时候觉得结论不够充分，还要再开个会话做额外的验证。目前 vibench 已经实现了通过 Issue 去提前记录和安排工作，然后在 Issue 里面实现能够自动流转的多阶段会话，我只需要在阶段中间介入，点一点按钮它就可以进行到下一个阶段。 到了第二个时期，痛点在于多线工作时常会产生阻塞。比方说我正在做任务 A，这时候想去做任务 B，我虽然可以先规划 B，却没法直接执行，因为我知道必须等 A 做完再去执行 B 是最好的。如果让它们两个同时在 Master 上工作又会容易产生冲突；但如果改用 Worktree，一个任务做完之后，我又可能会忘了去合并它——毕竟 Worktree 要合回 Master，也得等 Master 上的任务跑完。所以要持续追踪各项任务当前的进度。后来这个问题也在 vibench 里解决了，我给 Issue 增加了 Worktree 支持和排队功能：都在 Master 上工作的 Issue 可以排队等待；在 Worktree 上工作的 Issue 则可以并行推进，等合并到 Master 时再排队，并且排完一个就会自动让下一个开始工作。 到了第三个时期，我开始规划较大规模的任务。一个大任务同时包含几个不同方向的事情，比如设计、前端、后端，可能还有跟其他服务的对接。用项目管理的话说，我的工作单位从 Issue 上升到了 Epic 的工作。这个时期我喜欢先做完整的规划，一个 plan 里会分好几期来实现。我写了一个 herdr-coordinator Skill，它会启动一个专门用来做协调而不做实际开发的会话，通过 Herdr 去开新的 Tab，调用适当的 Agent 去安排工作，并监督把握当前整体的进展情况，持续推进这个任务。有的时候一个任务的周期可能会持续一两天之久。 这个时期的痛点在于，这种工作方式会导致我很难去了解当前的全局进展。有的时候工作进行到中段，一开就是上十个 Tab，每个 Tab 跑的事情都不同。在 Herdr 里看着望不到头的 tabs，根本无法知道发生了什么。有的时候某一个 Tab 需要去介入而我不知道，很容易因此而 Block 了别的 tab 的进展，浪费很多时间。你得不断地在大脑里构建出一个图景：哪些事情大致在做？然后手动去关注、点击，以确保它能够更好地按照自己的意愿工作。我感觉玩 RTS 多个基地同时发展 + 微操战斗都没有这么累。我也尝试过跟 Coordinator 说：“你自己来想办法帮我去回答问题和推进，不要让我介入。”但是这样做效果明显比我自己掌舵要差，有的时候会绕很大的路。说白了，它还未能具备足够好的自动驾驶能力。可它也未能提供让我能舒服地掌控全局的界面以及便捷的操作工具。 因此我就一直在思考，要自己实现一个 Coordinator 的 Agent Loop 和界面。正好这时候 Personal Agent 开始出现，它带来的体验革命就是全双工的会话，实际上它们的设计架构都大差不差。用过一些产品的读者都知道，它的主会话界面是不会阻塞消息的，无论它此刻在后台运行什么，你都可以顺畅地跟它沟通并且很快得到响应。它也有多会话的协调，无论是像 Raft 那样本身就有多个 agent 角色，还是像 Dots 那样只有单一的入口，底层都是主会话来协调多个 agent 的工作。 让我决定动手的时机是 DeepSeek 发表的《Super-agent 设计探索：迈向更自主的 Agent 系统》。我非常喜欢这种偏学术写作的文章，仔细地研读了好几遍。它概念清晰，引用了大量计算机工程的模式术语，不掺杂具体产品的包袱，直接帮我理顺了一套可以给 Coordinator 的通用抽象架构。 有一个原则，我从一开始就没有改变：我希望 vibench 这套系统始终只是去调用 Agent Harness，自己不要去实现一个 Harness。这就意味着我最终的预期是，我可以用 Claude Code 或者 Codex 来运行 Coordinator 的 Agent Loop。一个能够做协调的 Agent Loop 必须是有状态的，运行时与状态分离，能够在任何时候终止和恢复，脱离单个会话的生命周期限制。为此，其真正的核心状态的计算要与 Agent Loop 解耦，所有的操作都通过调用一个独立的组件的工具来进行。 定下大致目标后，我和 Fable 进行了好几轮探讨来定下整个架构。这里面我也遇到一些有趣的事情，比如说一开始 Fable 一次性地把所有的文档全部写了出来，但其实与我真实想要的东西相去甚远。后来我换了一种沟通方式，让它先把这件事情拆分成几个层面：从概念术语到数据模型，再到数据的流向。然后，每一个层面作为一个议题，每次只进行一个议题，不断提出问题并探讨清楚，且每个议题的最终成功不超过 500 字。 就这样，我跟他开了一天的会，从早上一直开到下午，才终于把整套系统的核心架构和基础梳理清楚。随后，我们基于这个基础进行了真正的项目产品需求探讨，之后又进入了设计界面的 mockup 阶段。直到现在，正式开发前的准备工作才算告一段落。 对我而言，这件事最大的收获和认知是：想和 agent 做好一个产品，还是要有耐心。不能一开始就急匆匆地把目标定得太远，指望着 Agent 一次性把所有东西都做好。虽然我自己对这一点本已有觉悟，但发现这次还是犯了类似的错误。当想要做的事情过于庞大，且没有现成的参考，更需要将其拆解成不同的阶段，慢慢地逐一探讨。 后来我回溯了这个过程中的 Token 消耗，发现实际上绝大部分都是“读”，真正让它“写”的东西其实很少。像是基础架构梳理的最终产物，其实只有六七个文件，每个文件只有 300 到 500 字。当我再回头看时，那确确实实是我能看懂、能理解，也完全符合我心意的文字。 这种掌控感让我非常有底气。我知道这是最核心的基石，而这些东西是我能看懂、能把握的，那么我相信基于它再往后延伸做出来的东西，也一定能最大程度地符合我的预期。 所以，Agent 做的东西并非那么不可控。如果想要做出可控的东西，就不能跳过中间环节，不要想着即便输入描述得再清楚，也能一步跳到最终的代码开发。中间还是要自己把握好最基础的定义。 就像洋葱一样，一层一层地包裹。如果最核心的每一个字你都能看懂，每一段话都符合你的想法，那么往外包的每一层也会尽可能地符合我们一开始所定下的形状，不会跑偏。 我在实际体验中也有这样的感觉。第一件事情花了接近两天，后面定 PRD 和设计都差不多在半个工作日内就解决了。后续的话，我相信只要我把 Tech Design 做完，就可以通过一次大的协调任务来等待它 Cooking，然后就可以用到最终的成果了。 所以，最大的功夫还是要花在开始，磨刀不误砍柴工。这有点像是小说里的炼丹：前期采药、配比、定顺序、看天时、控手法，把所有前置工作做到位，之后你才能长舒一口气，坐在一旁等着它慢慢炼，并能确信炼出的是你想要的东西。
